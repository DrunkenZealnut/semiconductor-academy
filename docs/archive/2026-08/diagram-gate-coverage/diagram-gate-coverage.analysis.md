원인은 `LayerStack`이 `wells`를 라벨보다 **나중에** 그리는데 층이 얕으면 라벨을 아래로 내려도 여전히 well 안이라는 것. 코드 주석은 "아래쪽으로 내려 겹침을 피한다"고 약속하고 있었지만 그 약속은 층이 충분히 높을 때만 지켜졌다.

**높이를 키워 피하지 않았다** — `vertical` 모드에서 층 두께는 막 두께라(usage.md §1) 얇은 표면층을 두껍게 그리면 도해가 거짓말을 한다. 라벨이 자리를 양보한다.

**이 과정에서 내 판정이 두 번 틀렸고 둘 다 실물이 잡았다.**

1. **세로 겹침만으로 판정** → 6건. `065-etching`은 라벨이 왼쪽·well이 가운데라 **정상**인데 오탐으로 올렸다. 가로를 넣어 4건.
2. **"가장 넓은 빈 자리"로 배치** → 멀쩡하던 `065-etching` 라벨이 오른쪽으로 끌려갔다. "왼쪽부터 처음"으로 바꿔 원위치(x=26).

또 하나: **서버가 옛 빌드를 물고 있어 "고쳤는데 그대로"인 스크린샷을 한 번 찍었다.** `pkill -f "SemiconductorAcademy.*next"`가 `next-server` 자식을 못 잡은 탓이다(그 프로세스 명령줄에 경로 문자열이 없다). 서버 시작 시각과 `.next/BUILD_ID` 시각을 비교해 확인했다 — **스크린샷이 최신 코드인지는 별도로 증명해야 한다.**

## 6. 이 사이클이 남기는 교훈

1. **검사를 느슨하게 바꿀 때는 음성 대조군이 필요하다.** 넓힐 때 양성을 더하는 것은 자연스럽지만, 느슨하게 할 때 "무엇을 이제 통과시키는가"를 고정하지 않으면 완화가 어디까지 갔는지 아무도 모른다. 이번에 C-8 2건·C-7 1건이 그랬다.
2. **제외가 여러 검사에 걸치면 걸치는 검사를 다 봐야 한다.** G-4 ②·⑤가 `C-2`만 보면서 D-1(C-6)·D-4′(C-8)의 절반씩을 증명하지 못한 채 ✅를 내고 있었다. 대조군이 **통과하는데도 공허한** 세 번째 방식이다(앞의 둘: 범위를 줄여 무효화, 건강한 검사가 0건을 내서 무효화).
3. **라벨을 쪼개는 규칙은 렌더러가 쪼개는 규칙과 같아야 한다.** 독자가 두 낱말로 읽는 것을 검사기가 한 낱말로 읽으면 오탐이 난다.
4. **좌표로 결정되는 겹침은 지금 어떤 검사도 보지 않는다.** 글자가 도형에 가려지는 것은 색 대비로도 폭 넘침으로도 나타나지 않는다 — G-9가 자동화로 대체되지 않는 이유의 실증이다.
5. **스크린샷은 최신 코드라는 증거가 아니다.** 서버 시작 시각과 빌드 시각을 대조하기 전까지는.
