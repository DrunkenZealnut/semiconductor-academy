## 1. 무엇을 만들었나

`scripts/verify-diagram-render.mjs` +248/−9. 핵심은 셋이다.

### 1.1 하네스 — 서버 없이 도는 이유

`measureInPage`는 `.toString()`으로 직렬화돼 `page.evaluate`에 들어간다. **같은 함수를** `page.setContent()`로 만든 도해에 먹일 수 있다. 대조군의 입력이 앱 상태가 아니라 **대조군 안에** 있으므로, 콘텐츠가 바뀌어도 대조군이 흔들리지 않는다(D-1).

색은 리터럴이 아니라 `node_modules/tailwindcss/theme.css`에서 읽는다(D-2) — 팔레트가 바뀌면 대조군이 따라간다. 실제 앱과 같은 oklch → canvas → sRGB 경로를 지난다.

### 1.2 `--self-test` 단독 실행

```bash
npm run verify:render -- --self-test   # Chrome만 필요
```

자격 증명 확인과 서버 탐지 **앞에서** 처리한다. 서버·자격 증명이 없는 자리에서도 검사기의 건강을 볼 수 있다(FR-5·G-5 실측 확인).

### 1.3 처분 — 자체검사가 실패하면 본 검사를 안 돌린다

`verify:diagram`과 같은 계약이다. **검사기가 눈먼 채로 "전 항목 통과"를 내지 않게.**

### 4.1 ①이 처음에 "안 깨졌다"고 나왔다 — 되돌림이 틀렸다

`out.figures += 1;`(137행) 바로 뒤에 `out.small.push({ …, cap })`을 넣었는데 **`cap`은 138행에서 선언된다.** TDZ로 `page.evaluate`가 통째로 터져 `❌ 실패` 줄이 **하나도** 안 나왔고, 스윕은 이것을 *"① 안 깨짐"* 으로 읽었다. 앵커를 `cap` 뒤로 옮기니 ①만 깨졌다.

## 7. 교훈

1. **문턱은 한쪽 끝에서만 보면 고정되지 않는다.** 대조군 ④는 *"잡는다"* 를 증명했지만 *"**4.5에서** 잡는다"* 는 증명하지 않았다. 같은 색을 써서 비율이 1.00이었기 때문이다. 문턱을 검사하는 대조군은 **반드시 양쪽**이어야 한다.
2. **처분은 감지와 다른 주장이다.** 두 사이클 전 정적 관문이 종료 코드 대조군 8건을 만들며 배운 것을, 렌더 쪽에서 **똑같이 다시 배웠다.** 규약을 문서에 적어 놓아도 **새 검사기에는 자동으로 옮겨지지 않는다.**
3. **재귀 회피는 매번 새로 설계해야 한다.** 세 번째다 — `--all`/`--assert-only`/`--self-test`. *"인자에 붙는 성질이지 코드베이스에 붙는 성질이 아니다."*
4. **fixture는 실제 형상을 흉내 내야 한다.** 11건 전부가 실제가 안 지나는 갈래를 지났고, 값이 우연히 같아 결과가 안 갈렸을 뿐이다.
5. **"게이트 7/7 충족"과 "대조군이 무엇을 고정하는지 안다"는 다른 문장이다.** Do는 앞의 것을, Check는 뒤의 것을 물었다.
6. **되돌림은 앵커의 위치까지 맞아야 한다.** §4의 ①이 처음에 "안 깨졌다"고 나온 것은 판정이 공허해서가 아니라 **되돌림이 TDZ를 만들어 `page.evaluate`가 통째로 터졌기** 때문이다. *"되돌렸는데 아무것도 안 깨졌다"* 는 두 가지를 뜻할 수 있다 — 대조군이 공허하거나, **되돌림이 틀렸거나.**
