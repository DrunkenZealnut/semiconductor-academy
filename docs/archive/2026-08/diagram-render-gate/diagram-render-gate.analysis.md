## 2. 이 Check의 핵심 사건 — 관문의 근거가 틀렸다 (H-1)

C-19가 `TONE × TEXT_MUTED` **26조합을 제외한 유일한 근거**는 Design D-9의 이 문장이었다.

> `LayerStack`의 `TEXT_MUTED` 3곳은 전부 층 밖이다 — … **L155는 좌상단 축 라벨(`x = 4`)**

**셋째는 층 밖이 아니었다.** `<defs>` 안 `<pattern>`의 마크 글리프(`+`/`−`)이고, `x={4} y={12}`는 절대 좌표가 아니라 **16×16 패턴 타일 안의 좌표**다. 그 패턴은 층 rect 위에 **같은 기하로 덮인다**.

```tsx
<pattern id={patternId(tone)} width={16} height={16} patternUnits="userSpaceOnUse">
  <text x={4} y={12} fontSize={11} className={TEXT_MUTED}>{TONE[tone].mark}</text>
</pattern>
…
{!isBand && tone.mark && <rect x={bodyX} y={y} width={bodyW} height={h} fill={`url(#${patternId(layer.tone)})`} />}
```

### 2.1 실측

| tone | 채움(라이트/다크) | `TEXT_MUTED` 라이트 | 다크 | `TEXT`로 바꾸면 |
|---|---|:--:|:--:|:--:|
| `silicon-p-heavy` | rose-300 / rose-800 | **3.94** ❌ | **3.01** ❌ | 7.63 / 7.23 |
| `silicon-n-heavy` | sky-300 / sky-800 | 4.54 ✅ | **2.86** ❌ | 8.80 / 6.86 |
| `silicon-p` | rose-100 / rose-950 | 6.29 | 5.96 | 12.19 / 14.28 |
| `silicon-n` | sky-100 / sky-950 | 6.58 | 5.29 | 12.76 / 12.68 |

**AA 미달 3건.** `mark`를 가진 tone은 4종뿐이고, `*-heavy` 2종은 **8건 5모듈**(`017-nmos`·`018-pmos`·`061-feol-2`·`066-doping` 등)에서 실제로 렌더되고 있었다. 전부 `orientation` 미지정(기본 `vertical`)이라 `!isBand`가 참이고 패턴이 적용된다.

### 2.2 왜 중요한가

마크는 장식이 아니다. `usage.md` §3의 **"색만으로 구분하지 않는다"**를 이행하는 **색각 이상 대비 장치**다. 읽히지 않으면 그 장치가 무력해지고, 색을 구별하지 못하는 독자에게 p형/n형은 같은 회색 층이 된다.

### 2.3 조치 순서 — 고치기 전에 검사가 잡는지 확인했다

```text
① 조합을 임시로 넓혀(--widen-tone-muted) 검사가 3건을 잡는지 확인
   → [C-19] silicon-p-heavy 3.94 · 3.01 · silicon-n-heavy 2.86  정확히 검출
   → 동시에 마크 없는 tone 오탐 7건도 확인 — 제외가 필요한 이유가 재확인됐다
② 글리프를 TEXT로 옮김
③ 실물 확인 (017-nmos 다크) — +/− 가 선명
④ 손으로 읽어 틀린 판단을 기계 규칙으로: checkPatternTextClass()
```

③을 ②보다 뒤에 둔 것이 아니라 **①을 ②보다 앞에 둔 것**이 요점이다. 검사가 잡지 못하는 상태에서 고치면 "고쳤다"는 사실만 남고 검사가 눈먼 것은 그대로 남는다.

### 2.4 D-12 스냅샷이 왜 못 잡았나

스냅샷은 **개수만** 본다. 글리프가 `TEXT_MUTED`였을 때 `LayerStack`의 사용처는 3이었고, Design이 기대한 값도 3이었다. **개수가 맞았기 때문에 침묵했다.**

Design §7이 적어 둔 한계("같은 개수로 위치만 옮기면 못 잡는다")와는 다르다. 이것은 **처음부터 위치를 잘못 읽은 경우**이고, 스냅샷은 그 오독을 검증하지 않는다. 그래서 `<pattern>` 안 글자를 보는 규칙을 붙였다 — 오독한 지점 하나를 기계 규칙으로 바꾼 것이다.

|---|---|
| **SVG 92페이지 중 60페이지가 C-1~C-17 범위 밖** | `first-semiconductor`가 `WAVES`에 없다. `CLAUDE.md`는 "도해를 추가·수정하면 `verify:diagram`"이라 적었는데 그 60모듈에는 C-1~C-17이 닿지 않는다(C-18·C-19는 컴포넌트·토큰 단위라 무관). 기준선 사이클은 임시 스크립트로 검사했고 그 스크립트는 남지 않았다 |

## 6. 교훈

### 6.1 제외의 근거는 검사보다 약하다

C-19의 36조합은 검사기가 계산한다. 그러나 **왜 26조합을 뺐는가**는 내가 소스를 손으로 읽고 판단한 것이었고, 그 판단이 틀렸다. 검사는 정확했고 **검사 범위를 정한 근거가 부정확했다.**

이 사이클에서 같은 유형이 두 번 나왔다.

| 시점 | 무엇을 손으로 읽었나 | 결과 |
|---|---|---|
| Design §0.1 | `badge`를 MDX에서 `badge:`로 세어 "사용 0건" | 실제 14건 — prop이 아니라 라벨 접두어였다 |
| Design D-9 | `<pattern>` 안 `x={4}`를 "좌상단 축 라벨"로 | 실제 층 채움 위 — 패턴 타일 좌표였다 |

둘 다 **파일을 봤는데 잘못 읽었다.** 처방도 같다 — 손으로 읽은 판단을 기계 규칙으로 바꾼다(`checkPatternTextClass`).

### 6.2 검사 범위를 줄이면 대조군이 조용히 무효해진다

조합 집합에서 ③(`NODE_KIND × TEXT_MUTED`)을 뺀 직후, 양성 대조군 "`TEXT_MUTED`를 `slate-500`으로 되돌림"이 **아무것도 검출하지 못했다**. `slate-500`은 남은 조합(프레임 배경)에서 4.76으로 통과하기 때문이다.

**본 검사는 그대로 통과하는데 자체검사가 먼저 실패했다.** 범위를 **넓힐** 때 대조군을 더하는 것은 자연스럽지만, **줄일** 때 기존 대조군이 무효해지는 것은 눈에 띄지 않는다.

### 6.3 손으로 센 수치가 또 틀렸다

이 사이클에서 세 번이다 — Design D-12 표의 `TEXT_MUTED` 계를 **12**로 적었으나 실측 **11**, Plan §3의 `badge` **0건**(실제 14), Design D-7의 **94페이지**(실제 92). `diagram-expansion` §4.3이 세운 규약("문서에 적는 수치는 검사기 출력을 옮긴다")을 세 번 어겼다.

스냅샷 값 자체는 맞았다 — 코드에는 `LayerStack: 2 … = 11`로 넣었고 검사가 통과했다. **틀린 것은 문서뿐이다.** 코드는 검사가 지키고 문서는 아무도 지키지 않는다는 것이 이 반복의 구조적 원인이다.

### 6.4 에이전트 결과를 두 번 다뤘다

| | 처리 |
|---|---|
| **첫 실행 실패** | 600초 무진행. 마지막 출력이 "The script file appears to have changed since my first read" — **에이전트가 분석 중인 파일을 내가 동시에 편집했다.** 도구가 경고한 그것이다. 결과 0건 |
| **재실행** | 기존 발견 4건을 브리핑에 넣어 중복을 배제하고, 내가 확인하지 않은 각도 4건을 지정 |
| **H-1** | 구조 3건·수치·사용량을 **직접 재확인한 뒤** 수용 |
| **H-2** | 지적의 프레임("Design은 36이라 적지 않았다")을 반박하고 산술만 수용 |
