## 한 줄 요약

시스템 소프트웨어 개발 = 장비를 실제로 움직이는 신경·뇌·얼굴을 만드는 일이에요. Library와 Device
Driver가 명령을 하드웨어가 알아듣는 신호로 바꾸고(신경), Main Controller가 센서 값을 읽어 무엇을 할지
판단하며(뇌), GUI가 그 판단을 사람이 보고 조작할 수 있는 화면으로 보여줘요(얼굴). 같은 반도체 장비
트랙의 다른 모듈이 장비를 설계하거나 조립·점검하는 일을 다룬다면, 이 모듈은 그렇게 만들어진 장비가
실제로 **"스스로 움직이고 판단하도록"** 만드는 소프트웨어를 다뤄요 — 장비 운영을 돕는 별도 지원
도구(유틸리티 소프트웨어)와는 구분되는, 장비 구동의 핵심부예요.

## 1. Library와 Device Driver — 장비의 신경, 명령을 신호로 바꾼다

명령을 내려도 그 명령이 실제 부품을 움직이는 전기 신호로 바뀌지 않으면 아무 일도 일어나지 않아요.
이 변환을 맡는 것이 Library와 Device Driver예요.

### 가. 시스템 소프트웨어 — 하드웨어를 깨우는 기초 프로그램

컴퓨터를 켜는 순간부터 시스템 소프트웨어가 움직여요. 기억 장치에 저장된 부팅 프로그램인
**펌웨어(Firmware)**, 사람이 쓴 코드를 기계어로 옮기는 **컴파일러**·**어셈블러**, 여러 조각
프로그램을 하나로 합치는 **링커(Linker)**, 이 모든 걸 조율해 사용자가 컴퓨터를 쓸 수 있게 하는
**운영 체제**까지 — 반도체 장비 한 대를 움직이려면 이 기초 부품들이 먼저 갖춰져 있어야 해요.

이 위에서 실제 개발자가 다루는 게 **라이브러리(Library)**예요. 다른 프로그램이 가져다 쓸 수 있도록
미리 만들어 둔 함수·서브루틴의 모음인데, 만들어진 형태에 따라 아래처럼 나뉘어요.

| 구분 | 형식 |
|---|---|
| 라이브러리 | 소스 형식 |
|  | 오브젝트 형식 |
|  | 로드 형식 |

<div className="text-xs italic text-slate-500">출처: NCS 학습모듈 반도체 장비 시스템 소프트웨어 개발 — 1-1. Library 개발 &lt;표 1-1&gt; 라이브러리의 형식</div>

**소스 형식**은 사람이 읽고 고칠 수 있는 원본 코드, **오브젝트 형식**은 컴파일러가 한 차례 번역한
중간 결과물, **로드 형식**은 실행 파일에 바로 붙여 쓸 수 있는 완성된 형태예요. 이 중에서도
**동적 링크 라이브러리(DLL)**는 프로그램이 실행되는 도중에 필요한 함수만 그때그때 불러 쓸 수 있어
메모리를 아낄 수 있다는 장점이 있어요.

### 나. Device Driver — 하드웨어와 소프트웨어 사이의 통역사

<SourceQuote section="NCS 학습모듈 — 반도체 장비 시스템 소프트웨어 개발: 1-1. Library 개발 (Device Driver)">
  <p>
    디바이스 드라이버(device driver)는 하드웨어가 최하위에 있고, 그 최상위에 응용 프로그램이
    실행되므로 응용 프로그램에서 직접 하드웨어를 제어하는 것이 아니라 디바이스 드라이버를 통해서
    하드웨어를 제어한다.
  </p>
</SourceQuote>

응용 프로그램은 모터나 센서를 직접 건드리지 않아요. 대신 그 장치 전용 통역사인 Device Driver에게
"이렇게 움직여라"라고 요청하면, 드라이버가 이를 실제 전기 신호로 바꿔 하드웨어에 전달해요. 반도체
장비는 장치 종류가 워낙 많아서 시리얼 통신 드라이버, 센서 드라이버, 파일 시스템 드라이버, 펌웨어
다운로드 드라이버 등 여러 종류가 함께 필요해요.

장비끼리 대화할 때는 업계 공통 규약도 따로 있어요. **SECS(SEMI Equipment Communications
Standard)**는 반도체·디스플레이 장비 사이의 표준 통신 프로토콜인데, 직렬 통신 기반의 SECS-I과
TCP/IP 기반의 HSMS 두 방식을 지원하는 XCom 같은 드라이버 하나로 최대 8개 통신 회선을 동시에
처리할 수 있어요. 회사마다 제각각인 장비들이 이 표준 덕분에 같은 언어로 소통할 수 있는 셈이에요.

<Callout type="info" title="PLC에서 PAC로 — 장비 두뇌의 진화">
  옛날 장비는 릴레이·타이머로 순서를 짜는 **PLC(Programmable Logic Controller)**로 움직였어요.
  요즘은 여기에 수치 연산과 복잡한 로직까지 더한 **PAC(Programmable Automation Controller)**로
  진화하고 있어요. LD(래더 다이어그램)·IL(명령어 방식) 같은 국제 표준 언어(IEC 1131-3)로 프로그램을
  짜는 건 여전히 비슷하지만, 다룰 수 있는 판단의 복잡도가 훨씬 커진 거예요.
</Callout>

## 2. Main Controller — 장비의 뇌, 센서 값을 판단으로 바꾼다

### 가. PID 제어로 오차를 줄인다

Main Controller는 가스·온도·압력·습도 같은 센서 신호를 ADC(아날로그-디지털 변환기)로 디지털
값으로 바꾼 다음, 그 값을 보고 무엇을 할지 결정해요. 반도체 생산 라인은 24시간 365일 멈추지
않기 때문에, 10밀리초 사이에 수십에서 수백 번씩 입출력을 처리할 만큼 빨라야 해요. 이때 널리 쓰이는
계산법이 **PID 제어**예요 — 목표값과 현재값의 차이(편차)에 그때그때 비례해서 반응하고(P), 오차가
누적된 만큼 더 보정하고(I), 변화하는 속도까지 예측해서(D) 최종 조작량을 계산해요. 자동차의
크루즈 컨트롤이 속도를 일정하게 유지하는 원리와 비슷해요.

이 판단이 왜 그렇게 중요할까요. 원문은 이렇게 설명해요.

<SourceQuote section="NCS 학습모듈 — 반도체 장비 시스템 소프트웨어 개발: 2-1. Main Controller 개발 (System 제어 구성)">
  <p>
    반도체 제조 공정에서 사용되는 gas 중에는 유독성 gas들이 포함되어 있어 미량만으로도 인체에
    치명적인 해를 입힐 수 있다. 또한 진공 상태에서 공정을 진행하고, 정확한 gas양과 온도, 압력
    그리고 플라즈마 상태에서 화학 반응이 일어나야 하므로 약간의 오차도 허용되지 않는다.
  </p>
</SourceQuote>

<Callout type="warning" title="소프트웨어의 오차가 곧 안전사고로 이어져요">
  <Term id="plasma">플라즈마</Term> 상태에서 화학 반응을 일으키는 공정은 gas양·온도·압력이 아주
  조금만 어긋나도 위험해질 수 있어요. Main Controller의 제어 알고리즘이 흔들리면 처리 중이던{' '}
  <Term id="wafer">웨이퍼</Term>가 통째로 불량 처리되는 데서 끝나지 않고, 새어 나온 유독 가스가
  작업자에게 그대로 노출될 수 있어요. 이 모듈에서 다루는 "정밀한 제어"는 품질 문제이자 동시에
  안전 문제예요.
</Callout>

### 나. 통신과 데이터로 장비 안팎을 잇는다

Main Controller는 혼자 일하지 않아요. 계측기와는 **GP-IB**(계측기용 표준 버스)로, 상위 시스템과는
**TCP/IP**로 연결되고, 장비 내부에서는 데이터 버스가 기억 장치와 처리 장치 사이의 신호를 실어
날라요. 이렇게 모인 데이터는 데이터베이스(DB)에 쌓여 운용자가 장비 상태를 조회하고 고장을 진단하는
데 쓰여요.

여러 공정 모듈이 한 몸처럼 붙어 있는 **클러스터 장비**에서는 전체를 감시하고 스케줄링하는
**CTC(Cluster Tool Controller)** 소프트웨어가 핵심이에요. 원문에 따르면 대당 수십억 원짜리
클러스터 장비에서 이 CTC SW 값이 전체 가격의 10% 이상을 차지할 만큼 비중이 커요 — 웨이퍼가 여러
공정 모듈을 오가며 대기 장소 없이 곧바로 다음 단계로 넘어가야 하니, 이 판단을 조금이라도 잘못하면
장비 전체가 멈추거나 웨이퍼가 손상될 수 있기 때문이에요.

## 3. GUI — 사람과 장비가 만나는 화면

### 가. 그래픽 유저 인터페이스의 구성

<SourceQuote section="NCS 학습모듈 — 반도체 장비 시스템 소프트웨어 개발: 3-1. GUI 개발 (GUI의 전체 구성)">
  <p>
    GUI(graphic user interface)는 사용자가 그래픽을 통해 컴퓨터와 정보를 교환하는 작업 환경을
    말한다. … 그래픽 유저 인터페이스에서는 마우스 등을 이용하여 화면의 메뉴 중에서 하나를 선택하여
    작업을 지시한다.
  </p>
</SourceQuote>

문자 명령어를 하나하나 외워 입력하던 시절과 달리, GUI는 버튼·아이콘·창(윈도)처럼 눈에 보이는
요소를 누르는 것만으로 장비에 지시를 내릴 수 있게 해줘요. 이걸 구현하는 GUI Library는 모노크롬부터
컬러까지 다양한 디스플레이를 지원하는 드라이버, 여러 창을 동시에 띄우는 **윈도 매니저**, 버튼·체크
박스 같은 **위젯**들로 이루어져 있고, 여기에 터치스크린을 쓰려면 눌린 위치를 좌표로 바꿔주는 별도의
입력 드라이버까지 더해져야 해요.

### 나. 현장에서 만들어진 진짜 시스템 소프트웨어

이 학습모듈의 원문에는 실제로 산업 현장에서 개발된 시스템 소프트웨어 사례가 나열돼 있어요. SMT
라인 관리 시스템(10개 라인), 제조 이력 관리 시스템, 3차원 인라인 X-ray 검사기, 휴대폰 조립 공정
핸들러(8축 로봇 제어, 총 80대) 소프트웨어, CVD·Sputter 장비의 HMI 제어, Cluster tool
인터페이스, 공정 자동화용 Vision 검사 프로그램까지 — 다루는 장비도, 언어도(C++·Visual
Basic·LabVIEW 등) 제각각이지만 공통점은 하나예요. **장비마다 다른 하드웨어를, 사람이 이해할 수
있는 하나의 화면으로 통일해서 보여준다**는 것이죠.

## 이 일을 하는 사람은

Library와 Device Driver는 주로 **임베디드 소프트웨어 엔지니어**가, Main Controller의 제어
알고리즘은 **장비 제어 SW 엔지니어**가, GUI는 **UI/애플리케이션 개발자**가 맡아요. 세 역할이
따로 노는 게 아니라, 장비를 설계하는 기구·전장 엔지니어가 넘겨준 사양서를 보고 "이 부품을 몇 밀리초
안에 어떻게 움직일지"를 함께 정해야 하기 때문에 하드웨어에 대한 이해도 함께 필요해요. 반도체 공정
자체를 몰라도 되는 일이 아니라, 가스·진공·온도 조건을 얼마나 정밀하게 지켜야 하는지 아는 사람이
더 안전한 소프트웨어를 만들어요.
