## 한 줄 요약

펌웨어는 반도체 칩에 전원이 들어오자마자 가장 먼저 깨어나 CPU와 주변장치를 쓸 수 있는 상태로
만드는 소프트웨어예요. 무엇을 만들지 정하고(요구 사항 분석) → 뼈대를 그리고(설계) → 코드로
옮기고(구현) → 하드웨어와 대화하는 통역사를 만들고(드라이버 개발) → 세상에 내보낸 뒤에도 계속
손보는(관리) 다섯 단계를 거쳐요. 「반도체 산업의 유해인자」<ChapterRef order={2} />가 "칩이 어떻게
만들어지는가"를 다룬다면, 이 모듈은 **"다 만들어진 칩을 어떻게 깨우고 움직이게 하나"**를 다뤄요.

## 1. 칩의 반사신경 — CPU와 주변장치를 깨우는 소프트웨어

### 가. CPU, 반도체 칩의 두뇌

<Term id="semiconductor">반도체</Term> 칩 안의 CPU(중앙 처리 장치)는 계산을 하는 손(연산 논리
장치, ALU), 지시를 내리는 지휘자(제어 장치), 순간적으로 메모하는 손바닥(레지스터), 자주 쓰는
물건을 가까이 두는 서랍(L1·L2·L3 캐시 메모리), 부품 사이를 잇는 도로(버스)로 이루어져요. 명령어를
가져오고(인출) → 뜻을 해석하고(해석) → 실제로 계산하고(실행) → 결과를 저장하는(저장) 네 박자를
쉬지 않고 반복하는 게 CPU의 일이에요.

<SourceQuote section="NCS 학습모듈 — 반도체 펌웨어 개발: 1-1. 내장 CPU 및 주변 장치 분석 (CPU 구조)">
  <p>
    CPU(central processing unit)는 컴퓨터의 두뇌 역할을 하며, 명령어를 해석하고 실행하는 장치이다.
  </p>
</SourceQuote>

### 나. 주변장치와 대화하는 법 — 메모리 맵과 레지스터

CPU 혼자서는 아무 일도 못 해요. 화면에 글자를 찍거나 통신선으로 데이터를 보내려면 주변장치와
대화해야 하는데, 이때 쓰는 방법이 세 가지예요. 주변장치 자리를 메모리 주소처럼 다루는 **메모리 맵
I/O**, CPU 전용 통로로 따로 관리하는 **포트 맵 I/O**, 그리고 주변장치가 "저요, 저요!" 하고 CPU를
직접 부르는 **인터럽트**예요.

<Callout type="info" title="메모리 맵과 레지스터란?">
  <strong>메모리 맵</strong>은 CPU가 쓰는 주소 공간에 ROM·RAM·주변장치가 각각 어느 번지에 사는지
  표시한 지도예요. 그 번지 안에는 주변장치의 상태·설정값을 담는 <strong>레지스터</strong>가 있어요.
  예를 들어 UART(시리얼 통신 장치)는 데이터를 담는 DR, 상태를 알려주는 SR, 설정을 바꾸는 CR
  레지스터를 갖고 있어서, CPU는 이 레지스터를 읽고 쓰는 것만으로 주변장치를 통째로 제어할 수 있어요.
</Callout>

### 다. 문제가 생기면 — 디버그 인터페이스로 속을 들여다본다

칩이 이상하게 동작하면 겉만 봐서는 원인을 알 수 없어요. 그래서 개발 보드에는 **디버그 인터페이스**
핀이 따로 나와 있어요. 신호선 5개(TCK·TMS·TDI·TDO·TRST)를 쓰는 **JTAG**와, ARM Cortex-M
계열에서 흔히 쓰는 2핀짜리 **SWD**(SWDIO·SWCLK)가 대표적이에요. 여기에 J-Link·ST-Link 같은
하드웨어 디버거와 GDB·OpenOCD 같은 소프트웨어 디버거를 연결하면, 코드를 한 줄씩 멈춰 세우고
레지스터·메모리 값을 실시간으로 들여다볼 수 있어요.

## 2. 무엇을 만들지 정하고 뼈대를 그리다 — 요구 사항 분석과 설계

### 가. 기능적 요구 사항과 비기능적 요구 사항

"UART로 데이터를 주고받을 수 있어야 한다"처럼 **펌웨어가 해야 할 일**을 정하는 게 기능적 요구
사항이고, "부팅은 2초 이내, 통신 속도는 115,200bps, 가동 시간은 99.9% 이상 보장"처럼 **얼마나
잘해야 하는지** 수치로 못 박는 게 비기능적 요구 사항이에요. 두 가지를 먼저 문서로 정리해야 개발
도중 혼란이 줄어요.

레퍼런스 보드(하드웨어와 펌웨어를 함께 시험해 보는 기준 보드)를 설계할 때도 같은 방식으로 요구
사항을 정리해요.

| 항목 | 예시 규격 |
|---|---|
| CPU | ARM Cortex-M4 기반 프로세서 |
| 메모리 | Flash 256KB, SRAM 64KB |
| GPIO | 20개 핀 |
| ADC | 12비트, 8채널 |
| 작동 온도 | -40°C ~ 85°C |
| 연속 작동 보증 | 1,000시간 이상 |

### 나. 부트로더와 부트 시퀀스 — 전원이 켜진 순간부터

전원이 들어오면 ROM이나 플래시 메모리에 있는 **1차 부트로더**가 먼저 깨어나 하드웨어를 최소한으로
정리한 뒤, 더 복잡한 초기화를 담당하는 **2차 부트로더**를 불러와요. 이 흐름 전체를 **부트
시퀀스**라 부르고, 전원 켜기 → 초기화 → 2차 부트로더 → 운영 체제(또는 펌웨어) 실행 순서로
진행돼요.

<SourceQuote section="NCS 학습모듈 — 반도체 펌웨어 개발: 2-1. 펌웨어 요구 사항 분석 (부트 로더와 부트 시퀀스)">
  <p>
    부트 로더는 시스템이 켜질 때 실행되는 첫 번째 코드로, 운영 체제나 펌웨어를 메모리에 로드하고
    실행하는 역할을 한다.
  </p>
</SourceQuote>

### 다. 레이어드 아키텍처로 설계하기

펌웨어를 한 덩어리로 짜면 나중에 다른 칩으로 옮기기가 지옥이 돼요. 그래서 흔히 **애플리케이션
레이어**(실제 하려는 일) → **드라이버 레이어**(UART·타이머 등 개별 장치 제어) →
**HAL(하드웨어 추상화 레이어)** → **하드웨어 레이어**(CPU·메모리·주변장치) 순서로 층을 나눠
설계해요. 아래층이 하드웨어의 지저분한 디테일을 감춰 주면, 위층은 "UART로 보내라"처럼 단순한
명령만 내리면 되죠. 이때 부팅 직후 가장 먼저 실행될 **Start-up 코드**(스택 포인터·벡터 테이블
설정, 클럭 설정, 메모리 초기화)도 함께 설계해요.

## 3. 코드로 옮기고, 하드웨어와 대화하는 통역사를 만들다 — 구현과 드라이버 개발

### 가. 테스트부터 계획하고 구현한다

펌웨어를 짜기 전에 **테스트 계획서**부터 써요. 부트로더 초기화, 메인 루프, 인터럽트 처리, 드라이버
초기화 같은 항목마다 "무엇을 입력하면 무엇이 나와야 성공인가"를 표로 정리하고, Unity·Google Test
같은 테스트 프레임워크로 자동화된 테스트 코드를 함께 만들어요. 하드웨어를 다루는 코드일수록 사람이
매번 눈으로 확인하기 어렵기 때문에, 테스트를 먼저 준비해 두는 습관이 특히 중요해요.

### 나. 드라이버 — 하드웨어의 사투리를 표준어로 통역하기

**드라이버**는 특정 주변장치(UART, SPI, I2C, GPIO 등)의 레지스터를 직접 만지고, 그 결과를 위쪽
소프트웨어가 이해하기 쉬운 표준 함수로 바꿔주는 통역사예요. 운영 체제의 핵심 영역에서 실행돼
속도가 빠른 **커널 모드 드라이버**와, 안정성을 우선하는 **유저 모드 드라이버**로 나뉘고, 대량의
데이터를 CPU 개입 없이 옮기는 **DMA(direct memory access)** 로 성능을 최적화하기도 해요.

<SourceQuote section="NCS 학습모듈 — 반도체 펌웨어 개발: 5-1. 펌웨어 드라이버 개발 (펌웨어 드라이버 개발 단계)">
  <p>
    반도체 펌웨어 드라이버 개발은 펌웨어가 하드웨어와 상호 작용할 수 있도록 하는 중요한 작업이다.
    펌웨어 드라이버는 하드웨어의 특정 기능을 제어하고 데이터 전송을 관리한다.
  </p>
</SourceQuote>

<Callout type="tip" title="RTOS는 왜 따로 있을까?">
  타이밍이 어긋나면 안 되는 임베디드 시스템에는 <strong>FreeRTOS</strong>·<strong>Zephyr</strong>
  같은 <strong>실시간 운영 체제(RTOS)</strong>를 쓰고, 처리 성능이 더 중요한 시스템에는 일반
  <strong>Linux</strong>나 <strong>Windows</strong>를 써요. 어떤 운영 체제를 고르느냐에 따라
  드라이버를 어떻게 설계할지, 그 운영 체제에 맞춰 커널을 옮겨 심는 <strong>포팅(Porting)</strong>
  작업까지 함께 결정돼요.
</Callout>

## 4. 세상에 내보내고 계속 돌보다 — 배포와 관리

### 가. 버전 관리와 릴리즈

펌웨어도 소프트웨어답게 **Git** 같은 버전 관리 시스템으로 코드 변화를 기록하고, 메인·개발·기능
브랜치로 나눠 작업해요. 릴리즈할 때는 1.0.0(첫 릴리즈) → 1.1.0(기능 추가) → 1.1.1(버그 수정)처럼
버전 번호를 규칙적으로 붙이고, 무엇이 바뀌었는지 릴리즈 노트에 남겨요.

<SourceQuote section="NCS 학습모듈 — 반도체 펌웨어 개발: 6-1. 펌웨어 관리 (반도체 펌웨어 관리 단계)">
  <p>
    반도체 펌웨어 관리는 펌웨어의 개발, 배포, 유지 보수 및 버전 관리를 포함하는 중요한 과정이다.
    이를 통해 안정적이고 신뢰할 수 있는 펌웨어를 제공하고, 지속해서 개선할 수 있다.
  </p>
</SourceQuote>

### 나. OTA 업데이트와 사용자 피드백

완성된 <Term id="semiconductor">반도체</Term> 제품이 출하된 뒤에도 일은 끝나지 않아요. 무선으로
펌웨어를 갈아 끼우는 **OTA(Over-The-Air) 업데이트**나 USB·JTAG로 직접 연결하는 방법으로
펌웨어를 배포하고, 사용자 피드백("통신 속도가 느리다", "특정 핀이 안 먹는다")을 모아 다음 버전에
반영해요. 실제 릴리즈 노트 예시를 보면 "UART 통신 속도를 9,600bps에서 115,200bps로 개선",
"GPIO 초기화 버그 수정"처럼 아주 구체적으로 기록해요.

<Callout type="warning" title="정전기 하나가 칩을 죽인다">
  펌웨어 개발의 모든 단계에서 빠지지 않는 안전 수칙이 <strong>정전기 방전(ESD) 방지</strong>예요.
  사람 몸의 정전기는 손끝으로 느껴지지 않을 정도로 작아도 칩 내부 회로를 순식간에 태워버릴 수 있어서,
  개발 보드와 계측 장비를 다룰 때는 접지·손목 스트랩 같은 기본 수칙을 항상 지켜야 해요.
</Callout>

## 이 일을 하는 사람은

CPU·주변장치를 분석하고 초기 코드를 짜는 사람은 **펌웨어 엔지니어**(임베디드 소프트웨어
엔지니어)라 불리고, 하드웨어별 통역기를 만드는 사람은 **드라이버 엔지니어**로 구분되기도 해요.
회로 설계자가 그린 칩을 실제로 "말귀 알아듣는" 물건으로 바꾸는 마지막 손길이 이 사람들 몫이에요.
