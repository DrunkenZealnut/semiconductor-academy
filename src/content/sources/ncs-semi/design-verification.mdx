## 한 줄 요약

반도체 설계 검증 = 완성된 회로 설계가 <strong>설계 사양대로 정말 동작하는지</strong> 단위
블록 → 통합 블록 → 플랫폼(FPGA 보드) 세 단계로 점점 크게 확인해 가는 과정이에요. <ChapterRef
order={2} />가 반도체 칩 자체가 무엇인지 다루고 검증 시나리오·검증 계획·테스트벤치·커버리지를
이 모듈이 다룬다면, 그 결과 확정된 설계가 실제 웨이퍼 위에서 어떤 공정을 거쳐 칩이 되는지는
<ChapterRef order={3} />에서 이어져요. 코드를 짜고 시뮬레이션을 돌리는 방법 자체보다는, "무엇을
확인할 것인가"와 "얼마나 확인해야 충분한가"라는 검증의 **방법론**에 초점을 맞춰요.

## 1. 검증은 왜 여러 번, 점점 크게 반복될까

### 가. 되돌릴 수 없는 공정이기 때문에

설계한 기능 블록이 목표한 대로 동작하는지는 반도체 제조 공정에 들어가기 훨씬 전에 확인을
끝내야 해요. 한 번 마스크를 만들어 웨이퍼를 찍기 시작하면 비용도 일정도 되돌리기 어렵기
때문이에요. 그래서 이 확인을 별도의 <strong>검증 시스템</strong>으로 구축해 두고, 회로
설계와는 독립적으로 꼼꼼히 돌려 보는 것이 효율적이에요.

<SourceQuote section="NCS 학습모듈 — 반도체 설계 검증: 필요 지식 (설계 검증 시스템)">
  <p>
    검증 시스템을 구축하는 목적은 설계한 기능 블록들이 설계 목표대로 정상적으로 동작하는지,
    동작상에 문제는 없는지 등에 대한 확인을 실시간으로 할 수 있는 검증 환경을 제공하는 데 있다.
  </p>
</SourceQuote>

### 나. 동작 시나리오 두 갈래 — 블록을 움직이는 법, 데이터가 흐르는 법

검증을 시작하려면 먼저 "무슨 동작을 확인할 것인가"부터 정해야 해요. 이걸 <strong>동작
시나리오</strong>라고 부르는데, 크게 두 갈래로 나뉘어요. 하나는 각 기능 블록에 제어 신호를
보내 원하는 동작을 하는지 확인하는 <strong>블록 제어 동작 시나리오</strong>이고, 다른 하나는
데이터가 여러 블록을 거쳐 흘러가는 전체 경로를 따라가며 확인하는 <strong>데이터 흐름 중심의
동작 시나리오</strong>예요.

<SourceQuote section="NCS 학습모듈 — 반도체 설계 검증: 필요 지식 (동작 시나리오의 구분)">
  <p>
    데이터 흐름 중심의 동작 시나리오는 입력되는 데이터가 하나의 기능 블록에서 처리되어 출력되고
    다음의 기능 블록으로 입력되는 것과 같이 데이터의 흐름을 중심으로 만드는 동작 시나리오이다.
  </p>
</SourceQuote>

  src="/source-images/ncs/design-verification/_page_21_Figure_0.jpeg"

CPU가 인터페이스를 세팅해 외부 데이터를 받아들이는 방식을 정의하면, 그 데이터는 버스 브리지와
기능 블록을 거쳐 DRAM에 기록돼요. 이어서 CPU가 그 데이터를 다시 읽어 처리한 뒤 결과를 DRAM에
저장하는 흐름까지 정상적으로 끝나야 이 시나리오는 "검증 완료"로 인정받아요. 이렇게 검증해야
할 시나리오를 다 정한 뒤에는, 모든 경우를 다 확인하기보다 핵심 시나리오를 골라 집중적으로
검증하는 편이 효율적이에요.

## 2. 검증 계획 세우기 — 무엇을 확인할 것인가

### 가. 기능·타이밍·전력·신뢰성, 네 개의 축

검증 계획은 보통 네 갈래로 나눠 세워요. 회로가 원하는 논리대로 동작하는지 보는
<strong>기능 검증</strong>, 클록 주기 안에서 신호가 제때 안정되는지 보는
<strong>타이밍 검증</strong>, 동작 중이거나 유휴 상태일 때 전력을 얼마나 쓰는지 보는
<strong>전력 검증</strong>, 정전기·고온저온·전자기 간섭 같은 극한 조건에서도 버티는지 보는
<strong>신뢰성 검증</strong>이에요. 이 네 축마다 기본 동작·경계 조건·예외 상황까지 나눠
구체적인 테스트 케이스를 정의하고, 어느 정도 확인해야 충분한지 커버리지 목표까지 미리
정해 둬요.

### 나. 설계 사양부터 다시 읽는다

검증 계획을 세우기 전에는 설계 사양 문서부터 다시 훑어요. 기능적 요구 사항, 클록 속도·전력
소비 같은 성능 요구 사항, 입출력 핀·통신 프로토콜 같은 인터페이스 요구 사항은 물론, 이 설계가
어떤 제조 공정 기술 노드로 찍히는지와 그에 딸린 <strong>디자인 룰</strong>, 레이어 정보까지
확인해야 해요. 디자인 룰은 배선 하나의 폭(Width)과 두 배선 사이 간격(Spacing), 서로 다른
레이어가 겹칠 때 확보해야 할 여유(Enclosure)처럼, 그 공정으로 실제 만들 수 있는 최소 치수를
정해 둔 규칙이에요.

## 3. 테스트벤치에서 UVM까지 — 검증 환경을 짓는 법

### 가. 테스트벤치, 다시 한번

검증 환경의 기본은 <strong>테스트벤치(Test Bench)</strong>예요. 검증 대상 회로인
DUT(Design Under Test)를 인스턴스화하고, 클록·리셋 신호를 만들어 공급하는 생성기, DUT에
다양한 입력을 흘려보내는 입력 자극기, DUT의 출력을 지켜보는 출력 모니터, 그 출력이 기대한
값과 맞는지 판정하는 검증 로직, 이 다섯 요소가 한 세트를 이뤄요.

### 나. 재사용 가능한 뼈대 — UVM

블록 하나짜리 테스트벤치는 직접 짜도 되지만, 여러 블록을 통합한 규모에서는 그때마다 새로
짜기가 비효율적이에요. 그래서 업계는 <strong>UVM(Universal Verification Methodology)</strong>이라는
표준화된 뼈대를 써요. 트랜잭션을 만들어 내는 Sequencer, 그 트랜잭션을 실제 신호로 바꿔 DUT에
넣어 주는 Driver, DUT의 출력을 관찰하는 Monitor, 기대값과 비교하는 Scoreboard처럼 역할이
이미 정해진 부품들을 조립하듯 검증 환경을 구성해요.

<SourceQuote section="NCS 학습모듈 — 반도체 설계 검증: 2-1. 통합 블록 검증 (테스트 벤치 — UVM 기반 테스트 벤치)">
  <p>
    UVM은 복잡한 테스트 벤치를 체계적으로 구성하고, 재사용 가능한 컴포넌트들을 통해 검증을
    효율적으로 수행할 수 있게 한다.
  </p>
</SourceQuote>

부품을 새로 깎지 않고 표준 규격 나사와 브래킷을 조합해 가구를 짜듯이, UVM은 Driver·Monitor·
Scoreboard 같은 표준 부품을 다른 프로젝트에서도 그대로 가져다 쓸 수 있게 해 줘요. 그래서
검증 대상 블록이 바뀌어도 검증 환경 전체를 처음부터 다시 짤 필요가 없어요.

## 4. 다 확인했다는 걸 어떻게 알까 — 커버리지와 마지막 관문

### 가. 코드 커버리지와 기능 커버리지

시뮬레이션을 아무리 많이 돌려도 "얼마나 충분히 확인했는지" 숫자로 재지 않으면 검증이 끝났다고
말할 수 없어요. 그래서 두 가지 커버리지를 함께 봐요. RTL 코드의 모든 줄·조건·상태가 실제로
한 번씩은 실행됐는지 보는 <strong>코드 커버리지</strong>와, 설계 사양에 적힌 기능 요구
사항을 하나도 빠짐없이 테스트했는지 보는 <strong>기능 커버리지</strong>예요. 간단한 8비트
가산기 예제를 검증한 뒤 남긴 리포트를 보면 이 두 수치가 나란히 어떻게 기록되는지 알 수 있어요.

| 항목 | 예시 결과 |
|---|---|
| 검증 대상 | adder (가산기) |
| 검증 목표 | 기능, 타이밍, 전력 검증 |
| 전체 테스트 케이스 | 3개 중 3개 성공, 0개 실패 |
| 코드 커버리지 | 100% |
| 기능 커버리지 | 100% |

<div className="text-xs italic text-slate-500">출처: NCS 학습모듈 반도체 설계 검증 — 2-1. 통합 블록 검증 (검증 결과 분석 및 피드백) 예시 검증 리포트를 표로 재구성</div>

두 수치가 모두 100%에 가까워야 "설계는 모든 기능 요구 사항을 충족하였다"는 결론을 내릴 수
있어요. 검증 중 문제가 발견되면 디버깅하고, 수정된 설계를 다시 검증하는 과정을 반복해요.

### 나. 마지막 관문 — 진짜 하드웨어에 올려 보기

단위 블록과 통합 블록을 시뮬레이션으로 다 확인했어도, 마지막 한 단계가 남아 있어요. 실제
하드웨어처럼 동작시켜 보는 <strong>플랫폼 기반 검증</strong>이에요. 이때 쓰는 검증 플랫폼
보드는 설계를 실시간으로 흉내 내는 <strong>FPGA</strong>, 보드를 제어하는 프로세서와
메모리, 안정된 전압을 공급하는 전원 회로, 디버깅용 JTAG와 데이터 전송용 USB·Ethernet 같은
인터페이스, 그리고 상태를 보여 주는 LED·디스플레이로 구성돼요.

<SourceQuote section="NCS 학습모듈 — 반도체 설계 검증: 3-1. 플랫폼 기반 검증 (검증 플랫폼 보드 구성)">
  <p>설계된 반도체 칩의 기능을 에뮬레이션(emulation)하는 데 사용된다.</p>
</SourceQuote>

시뮬레이션에서는 며칠씩 걸리는 검증도 FPGA 보드 위에서는 실시간으로 돌려 볼 수 있어요.
시뮬레이션 결과와 실제 하드웨어 동작을 맞대어 보고, 로직 분석기로 내부 신호까지 들여다본
뒤에야 비로소 이 설계는 값비싼 제조 공정으로 넘어갈 준비가 끝나요.

## 이 일을 하는 사람은

단위 블록 하나하나를 시뮬레이션으로 확인하는 사람은 <strong>검증(Verification) 엔지니어</strong>,
UVM 같은 재사용 가능한 검증 환경을 설계하는 사람은 <strong>검증 환경 엔지니어</strong>라 불려요.
플랫폼 기반 검증 단계에 오면 FPGA 보드에 직접 설계를 올리고 로직 분석기로 신호를 들여다보는
<strong>FPGA 검증 엔지니어</strong>가 합류하고요. 이들은 대부분 컴퓨터와 시뮬레이터, FPGA
보드 앞에서 일하는 만큼 <Term id="semiconductor">반도체</Term> 공장의 화학물질보다는 정전기
